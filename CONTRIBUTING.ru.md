# Как участвовать

> English version: [CONTRIBUTING.md](./CONTRIBUTING.md)

- Расширение — клиент сервиса sir. Правила версий sir — версия пакета, протокол, схема
  конфига, формат патча — описаны в
  [VERSIONING.md](https://github.com/Danil-Varakin/S.I.R/blob/main/VERSIONING.md) ядра
  и обязательны здесь так же, как в ядре. Ниже — правила, относящиеся только к расширению.
- Устройство кода описано в [ARCHITECTURE.md](./ARCHITECTURE.md).

## Подготовка

Нужно: Node.js 22 и npm, git, VS Code 1.101 или новее.

```bash
npm install
```

`npm install` ставит ядро тарболом релиза, названным в `package.json`
(`dependencies.sirp`).

| Скрипт | Что делает |
|---|---|
| `npm run build` | порождает `syntaxes/sir.tmLanguage.json` и собирает `src/extension.ts` в `dist/extension.cjs` |
| `npm run watch` | пересобирает бандл при каждом изменении исходников; грамматика не пересоздаётся |
| `npm run grammar` | пересоздаёт `syntaxes/sir.tmLanguage.json` по реестру языков установленного ядра |
| `npm run typecheck` | `tsc` по проекту |
| `npm test` | модульные тесты, `node --test` по `test/**/*.test.ts`, без редактора |
| `npm run check` | `typecheck`, затем `test` |
| `npm run test:perf` | `npm test` с `SIR_PERF=1`: тесты проверяют ещё и время, как в CI |
| `npm run test:e2e` | `build`, затем сквозные тесты в настоящем VS Code; первый запуск скачивает VS Code в `.vscode-test/` |
| `npm run package` | `build`, проверка состава пакета, затем `sir-vscode-<версия>.vsix` |
| `npm run test:packaged` | ставит `.vsix`, записанный `package`, в одноразовый профиль и запускает в нём сквозные тесты |
| `npm run coverage` | модульные тесты под c8 и сквозные под `vscode-test --coverage`, сведённые в один отчёт по `src/`: `coverage/index.html` |
| `npm run test:mutation` | мутационное тестирование чистых модулей (Stryker, `stryker.config.mjs`); отчёт — `reports/mutation/mutation.html` |

**F5** открывает окно *Extension Development Host* (`.vscode/launch.json`; перед запуском
выполняется задача `build`). То же окно из терминала:

```bash
code --extensionDevelopmentPath=. /путь/к/проекту
```

Изменения кода и манифеста вступают в силу после **Developer: Reload Window** в этом окне.

### Локальное ядро

Для работы против ядра, которое меняется одновременно с расширением, клон ядра кладётся
рядом с этим и подключается ссылкой без изменения манифеста:

```
some-dir/
├── S.I.R/                  git clone https://github.com/Danil-Varakin/S.I.R S.I.R
│                             npm install && npm run build
└── S.I.R-VScodeExtension/    этот репозиторий
```

```bash
npm install --no-save ../S.I.R   # node_modules/sir становится ссылкой на клон
```

- Тогда всё здесь запускает ядро из `S.I.R/dist`; после правки или `git pull` в ядре
  сначала выполняется `npm run build` в `S.I.R`.
- `npm install` без флага возвращает выпущенное ядро.
- `npm run package` отказывается работать, пока `node_modules/sir` — ссылка (см.
  [Сборка пакета](#сборка-пакета)).

## Сборка пакета

Пакет собирается только против выпущенного ядра:

```bash
npm install             # выпущенное ядро
npm run package         # бандл, проверка состава, sir-vscode-<версия>.vsix
npm run test:packaged   # сквозные тесты против установленного .vsix
```

- **Ссылка на ядро не принимается.** vsce не допускает путей выше корня пакета, а ссылка
  принесла бы сборочное дерево ядра и его dev-зависимости вместо его пакета.
- **Состав проверяется** перед записью `.vsix` (`scripts/package-contents.mjs`): внутри
  должны быть бандл, файлы, на которые ссылается манифест, точка входа сервиса ядра и его
  грамматики; исходники, тесты, локальная `docs/` и документы для участников в пакет не
  попадают (`.vscodeignore`).
- **Файла LICENSE нет.** В репозитории его нет, поэтому пакет пишется с `skipLicense`.

## Непрерывная интеграция

`.github/workflows/ci.yml` запускается на каждый push и pull request:

| Задача | Где | Что |
|---|---|---|
| `test` | Linux, macOS, Windows × два ядра: `release` (названное в `package.json`) и `dev` (ветка `dev` sirTs или ревизия, указанная при ручном запуске) | `npm run check`; на Linux и Windows также `npm run test:e2e` |
| `package` | Linux, после `test` | `npm run package` с выпущенным ядром; `.vsix` сохраняется как артефакт сборки |
| `packaged` | Linux, Windows, после `package` | `npm run test:packaged` против этого `.vsix` |

Сквозные тесты не запускаются на macOS-раннере: редактор сообщает расширениям активный
редактор только пока его окно в фокусе, а у этого раннера окна в фокусе нет. На macOS
тесты запускаются вручную перед выпуском.

`.github/workflows/release.yml` запускается на тег `v*`:

1. Тег должен совпадать с `v` + версия из `package.json`; иначе запуск завершается ошибкой.
2. `npm run check`, `npm run test:e2e`, `npm run package`, `npm run test:packaged`.
3. `.vsix` прикрепляется к GitHub Release этого тега.

В Marketplace и Open VSX ничего не публикуется.

## Архитектурное правило

**В расширении нет логики S.I.R.** Оно не разбирает `.sirp`, не сопоставляет шаблоны, не
переносит позиции между версиями файла, не определяет, куда кладётся патч и к какому файлу
он относится. Оно спрашивает ядро (`generate`, `resolve`, `apply`, `config`, `pair`) и
показывает ответ.

- Вторая копия любого из этих правил незаметно разойдётся с ядром и начнёт выдавать
  правдоподобные, но неверные координаты.
- Если функции, по-видимому, нужно такое правило, оно добавляется в ядро, а расширение
  получает его через протокол.

Второе правило: **никогда не переходить «туда, где похоже».** Любой ответ — точное место,
место, названное приблизительным, или отказ с причиной и следующим шагом.

## Диапазон протокола (R7–R9)

R7–R9 — правила VERSIONING.md для клиентов протокола.

- Расширение объявляет **диапазон** `SUPPORTED_PROTOCOL = { min, max }` в
  `src/service/protocol.ts`: `max` — новейший протокол, против которого оно написано и
  проверено; `min` — старейшее ядро, с которым оно ещё работает.
- Совместимо с ядром, если диапазоны пересекаются: `min ≤ protocol` и
  `protocolMin ≤ max`. Ядро без `protocolMin` (протокол 2 и старше) читается как
  `protocolMin = protocol`.
- **Номера протокола никогда не сравниваются на равенство** (R9): такая проверка ломает
  расширение на каждом подъёме протокола, даже совместимом.
- `max` поднимается только после прогона тестов против ядра с этим протоколом. `min`
  поднимается только когда расширение начинает пользоваться тем, чего у старых ядер нет, и
  тогда это ломающее изменение для расширения.
- Рабочий протокол — `min(protocol ядра, max)`. Возможность протокола новее `min`
  используется, только если ядро объявило этот протокол.
- Пути в запросах — только абсолютные (протокол 2): у сервиса нет своей рабочей папки.
- Типы протокола реэкспортируются из `sir/protocol`, а не копируются, поэтому
  расхождение с ядром — ошибка компиляции. Исключение: поле протокола новее поставляемого
  ядра описывается в `src/service/protocol.ts` — необязательным и с номером протокола в
  имени (`ConfigResultV5`, `GenerateParamsV5`) — и удаляется, когда зависимость переходит
  на ядро, в котором оно есть.

## Настройки редактора повторяют конфиг (E1)

- У каждого ключа `generate.*` из `sir.config.json` — настройка `sir.*` с тем же путём
  без `generate.` (`generate.base.eol` → `sir.base.eol`), с тем же смыслом и теми же
  значениями. По умолчанию она не задана (`null` или пустая строка), и тогда решает
  конфиг; заданная — перекрывает конфиг только для этого человека, как флаг CLI.
- Настройка выходит **в том же выпуске**, что и поддержка схемы конфига, в которой
  появился ключ. Удалённый или переименованный в ядре ключ так же удаляется или
  переименовывается здесь.
- Настроек `sir.*`, которых нет в конфиге, не заводить. Исключение вписывается сюда с
  причиной до того, как настройка выходит.
- Значение по умолчанию — как в ядре, кроме перечисленного здесь, с причиной:
  - `base.eol`: если не задано ни настройкой, ни конфигом, расширение шлёт `worktree`, а
    ядро и CLI по умолчанию берут `repository`. Причина: расширение сравнивает с
    буфером, а буфер — это файл с диска; при `core.autocrlf` база с окончаниями
    репозитория сделала бы изменённой каждую строку.
- `test/settings-config.test.ts` сверяет `package.json` с новейшей схемой конфига ядра, с
  которым собрано расширение, а настройки, запрещённые недоверенному workspace, — с теми,
  что код там игнорирует.

## Тесты

`npm test` работает без редактора:

- **Чистые модули** — выбор ханка, подрезка краёв, хранилище таблиц, вердикты, настройки,
  решение Apply — тестируются изолированно. Поэтому новая логика размещается в чистых
  модулях: код, связанный с редактором, остаётся тонким.
- **Против настоящего ядра** — клиент, `config`/`pair`/`resolve`, координаты, на которые
  опирается навигация. Координаты никогда не проверяются на рукописных фикстурах: ханк,
  написанный вручную, может согласоваться с тестом и разойтись с сервисом.
- **Против подставного ядра** (`test/fixtures/fake-service.mjs`,
  `test/fixtures/scripted-service.mjs`) — только поведение, которое настоящее ядро не
  воспроизводит по запросу: `generate`, работающий до отмены, ядро без `cancel`, ядро,
  которое не останавливается.

`npm run test:e2e` запускает расширение в настоящем VS Code (`@vscode/test-cli`):

- `test/e2e/fixture.mjs` при каждом запуске создаёт свежие workspace во временной папке:
  репозиторий с базой из git, проект над `upstream`, папку без git и workspace `quiet`, где
  нет ничего от sir.
- Тесты в `test/e2e/*.e2e.ts` управляют расширением только через его команды и то, что
  показывает VS Code: линзы, Problems, Outline, строку состояния, diff, окна сообщений (на
  них отвечает заглушка).
- `activate` возвращает тестам несколько хуков только для чтения (`SirTestApi`): число
  запущенных ядер, ворота, текст строки состояния, таблицу патча, состояние патча.
- Функция, которая что-то показывает в редакторе, добавляется вместе со своим сквозным
  тестом.

То, до чего команды не дотягиваются, — вид линзы или значка, место пункта контекстного
меню, — проверяется вручную в окне разработки.

`npm run test:mutation` (Stryker) по одной вносит в чистые модули мелкие ошибки и гоняет
`npm test`; ошибка, которую не заметил ни один тест, — это недостающий тест. Прогон
занимает минуты, поэтому запускается вручную, не в CI, и падает при доле убитых мутантов
ниже 80%. Мутируются только модули, до которых дотягиваются модульные тесты (список — в
`stryker.config.mjs`): новый чистый модуль добавляется туда.

## Перед тем как изменение войдёт

- `npm run check` проходит; при подключённом ссылкой ядре — после `npm run build` в ядре.
- `README.md` и `README.ru.md` меняются вместе; `CONTRIBUTING.md` и `CONTRIBUTING.ru.md` —
  тоже.
- У видимого пользователю изменения есть запись в `CHANGELOG.md` в разделе *Unreleased*,
  ломающие изменения — первыми.
- Новая настройка — по E1; новый метод или поле протокола используется только после того,
  как его покрывает `max`.
- Идентификатор команды пишется в `package.json` и в `src/commands/ids.ts`, больше нигде.

## Выпуски

- `CHANGELOG.md` называет для каждого выпуска четыре числа: версию расширения, диапазон
  протокола, на котором оно работает, схему конфига, которую повторяют его настройки, и
  формат патча, который подсвечивает его грамматика.
- **Версия расширения.** До 1.0.0 любая новая функция и любое ломающее изменение поднимают
  minor (0.1.0 → 0.2.0), одно исправление — patch (0.1.0 → 0.1.1). С 1.0.0 — semver:
  ломающее — major, функция — minor, исправление — patch.
- **Ломающее для расширения:** подъём `min` диапазона протокола (старый sir перестаёт
  работать); удаление или переименование настройки `sir.*`, id команды или сочетания
  клавиш; прекращение поддержки схемы конфига или формата патча. Каждое пишется в
  CHANGELOG под *Breaking* с указанием, что делать.
- **Функция:** подъём `max` диапазона протокола, настройка для нового ключа конфига (E1),
  новая команда.
- `.vsix` несёт ядро, с которым его проверили; версия ядра называется в записи CHANGELOG, а
  `max` поднимается только после `npm run check` и `npm run test:e2e` против него (R7).
- Выпуск расширения, работающий на новом протоколе, выходит раньше или вместе с sir,
  который поднимает `protocolMin` (VERSIONING.md, S3); таблица *Clients* там обновляется
  вместе с ним.
- Выпуск делается push'ем тега `v<версия>`; см.
  [Непрерывная интеграция](#непрерывная-интеграция).
