# S.I.R для VS Code

Структурные патчи для исходного кода в редакторе. Патч
[sir](https://github.com/Danil-Varakin/S.I.R) задаёт место правки через структуру
самого кода — объемлющие блоки и соседние строки, — а не через номера строк, и ядро
находит это место в текущей версии файла.

> English version: [README.md](./README.md)

Что делает расширение:

- **Порождает патч по правкам.** Новая версия — буфер редактора, включая несохранённое;
  старая — база: файл, сохранённый на диске, или ревизия git.
- **Связывает патч и его код.** Одно сочетание клавиш переводит из ханка в изменяемый им
  код и обратно; другое открывает diff того, что ханк заменяет. Связь работает сразу после
  открытия файла, без предварительной генерации.
- **Показывает состояние патча.** Ложится ли каждый ханк, куда именно и есть ли патч уже в
  коде — в самом патче, в Problems, в Explorer и в строке состояния.
- **Применяет патч к его коду** — к одному файлу или ко всему workspace.

Собственной логики патчей в расширении нет: разбор, сопоставление, место патча и его
целевой файл — ответы ядра sir, которое работает дочерним процессом.

## Установка

| Что | Для чего | Что нужно в системе |
|---|---|---|
| [`.vsix` из релиза на GitHub](https://github.com/Danil-Varakin/S.I.R-VScodeExtension/releases) | написание и сопровождение патчей в VS Code | VS Code 1.101 или новее. Ядро sir и его грамматики tree-sitter лежат внутри пакета и работают на Node самого редактора: ни Node в системе, ни сеть не нужны |
| [Исходники расширения](https://github.com/Danil-Varakin/S.I.R-VScodeExtension) | доработка расширения | Node.js 22 и npm, git, VS Code 1.101 или новее; см. [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md) |
| [sir — ядро и его CLI](https://github.com/Danil-Varakin/S.I.R) | генерация и применение патчей в терминале, скрипте сборки или CI; доработка ядра | как описано в его README |

В Marketplace и Open VSX расширение не опубликовано. Установка `.vsix`:

1. Скачать `sir-vscode-<версия>.vsix` со страницы
   [Releases](https://github.com/Danil-Varakin/S.I.R-VScodeExtension/releases).
2. В VS Code: **Extensions** (`Ctrl+Shift+X`, на macOS `⇧⌘X`) → **…** в шапке панели →
   **Install from VSIX…** → скачанный файл.

То же из терминала, если команда `code` есть в PATH (её ставит команда палитры
**Shell Command: Install 'code' command in PATH**):

```bash
code --install-extension sir-vscode-0.1.0.vsix
```

- Установка поверх той же версии требует `--force`.
- Удаление: `code --uninstall-extension danil-varakin.sir-vscode`. Настройки `sir.*`
  остаются в `settings.json`.
- В удалённом окне (SSH, WSL, контейнер) расширение работает на удалённой стороне.
  Виртуальные workspace не поддерживаются: ядру нужны файлы на настоящей файловой системе.

Расширение активируется, когда в workspace есть `sir.config.json`, когда открыт файл
`.sirp` или по первой команде S.I.R. До этого оно не запускает процессов и не добавляет
пунктов в контекстные меню.

## Команды

| Команда | Сочетание | Где | Что делает |
|---|---|---|---|
| **Sir: Generate Patch** | `Alt+G`, на macOS `⌥⌘G` | палитра, заголовок редактора, контекстное меню файла кода в Explorer и его вкладки | Сравнивает буфер (для неоткрытого файла — его текст на диске) с базой, пишет патч туда, куда проект кладёт патчи, и открывает его рядом с кодом. Существующий патч файла перегенерируется, второй не создаётся |
| **Sir: Generate Patch Against File…** | — | палитра | Запрашивает старый файл и порождает патч против него вместо базы — только для этого запуска |
| **Sir: New S.I.R Patch** | — | палитра, контекстное меню файла кода в Explorer и его вкладки | Открывает несохранённый патч там, куда его записал бы Generate Patch: шапка и один ханк, якоря которого — позиции табуляции сниппета. Если у файла уже есть патч, открывается он |
| **Sir: Continue Generate** | — | линза **▶ Continue Generate** над черновиком, палитра | Отправляет черновик **Write by Hand** в ядро и продолжает синтез от него (см. [Когда синтез не может привязать правку](#когда-синтез-не-может-привязать-правку)) |
| **Sir: Go to the Other Side** | `Alt+O`, на macOS `⌥⌘O` | палитра | Из ханка — в изменяемый им код; из кода или из половины diff с базой — в его ханк |
| **Sir: Go to What the Hunk Replaces** | `Alt+B`, на macOS `⌥⌘B` | палитра | Открывает diff «база ↔ база + патч», ханк отмечен с обеих сторон: его строки в рамке, после первой — `◀ hunk N of M`, метка на полосе прокрутки. Где ханк ничего не занимает — в базе у вставки, в результате у удаления, — место отмечено чертой между строками. Отметка держится, пока открыт diff и не изменился патч |
| **Sir: Preview Patch** | — | палитра | Тот же diff для всего патча: что запишет сборка. Ничего не записывается |
| **Sir: Show Edits Not in Patch** | — | палитра, сторож в строке состояния | Diff «база + патч ↔ файл»: правки в коде, которых нет в патче |
| **Sir: Apply Patch** | `Alt+A`, на macOS `⌥⌘A` | палитра, заголовок `.sirp`, линза над шапкой, панель S.I.R Patches | Накладывает патч на его базу из git и ставит результат на место кода, без сохранения (см. [Применение патчей](#применение-патчей)) |
| **Sir: Apply All Patches** | — | палитра, панель S.I.R Patches | Apply Patch для каждого `.sirp` workspace; сводка перечисляет пропущенные патчи с причиной для каждого |
| **Sir: Check All Patches** | — | палитра, панель S.I.R Patches | Проверяет каждый `.sirp` workspace против базы проекта. Результат: панель S.I.R Patches в Explorer, Problems, красные имена файлов в Explorer |
| **Sir: Copy Patch Report** | — | палитра, панель S.I.R Patches | Копирует последнюю проверку в Markdown: итоги и каждый патч, требующий внимания |
| **Sir: Open Failed Patches** | — | палитра, панель S.I.R Patches | Открывает все патчи, которые последняя проверка признала неприменимыми |
| **Sir: Show Base** | — | палитра, база в строке состояния | Пишет в журнал, с какой базой сравнит генерация из активного файла и откуда взято каждое значение `generate.base` |
| **Sir: Init Config** | — | палитра, только доверенный workspace | Создаёт `sir.config.json` в корне репозитория и открывает его (см. [Init Config](#init-config)) |
| **Sir: Show Log** | — | палитра, строка состояния | Открывает канал вывода *S.I.R* |

Каждое сочетание — три клавиши. На macOS в каждое входит Command, потому что Option с
буквой печатает символ (`⌥O` — это `ø`). Назначить или переназначить команду можно в
**Preferences: Open Keyboard Shortcuts**.

### Init Config

**Sir: Init Config** создаёт минимальный корректный `sir.config.json`; опций у команды
нет.

- **Где:** в корне репозитория активного файла; если файл не открыт — единственной папки
  workspace.
- **Содержимое:** `$schema` и `version` новейшей схемы конфига, которую читает ядро;
  остальные ключи сохраняют значения по умолчанию. Текст составляет ядро.
- **Если файл уже есть:** он открывается и не перезаписывается.
- **В недоверенном workspace:** команда отказывает и ничего не пишет.

## База

База — старая версия, против которой вычисляется и на которую накладывается патч.

| База | Как задаётся | Что тогда описывает патч |
|---|---|---|
| сохранённый файл (по умолчанию) | ничего не задано | несохранённые правки буфера |
| последний коммит текущей ветки | `generate.base.head: true` или `sir.base.head: true` | буфер относительно этого коммита |
| последний коммит ветки | `generate.base.branch` или `sir.base.branch` (`main`, `origin/main`) | буфер относительно этой ветки |
| коммит | `generate.base.commit` или `sir.base.commit` (sha, тег, `HEAD~3`) | буфер относительно этого коммита |

Проект задаёт базу один раз, в `sir.config.json`:

```jsonc
{ "version": 3, "generate": { "base": { "head": true } } }
```

- Строка состояния показывает базу активного файла, например `base HEAD:src/a.cc @
  4f1c2e2`, и пересчитывает её после коммита или смены ветки.
- Базу из git, которую нельзя прочитать (файл не закоммичен, ветки или коммита нет в
  репозитории), расширение называет в сообщении и в строке состояния. Сохранённым файлом
  она не подменяется никогда.
- Если буфер равен базе, патч не пишется: `a.cc matches HEAD:src/a.cc, nothing to patch`.
- **Generate Patch Against File…** использует выбранный файл на один запуск. Следующий
  Generate Patch, навигация и проверки снова используют базу.

## Куда попадают патчи

Патч — файл `.sirp`. Его место определяет ядро, поэтому расширение пишет ровно туда же,
куда записал бы CLI. Место задают два ключа `sir.config.json`:

- `generate.out` — место патчей. Путь, оканчивающийся на `.sirp`, — это файл, он берётся
  как есть. Любое другое значение — имя без расширения, путь со `/` на конце, существующая
  папка — это папка, и патч в ней называется `<имя файла>.sirp`. Относительный путь
  отсчитывается от корня репозитория. Недостающие папки создаются. Если ключ не задан,
  патч кладётся рядом со своим файлом.
- `upstream` — корень кода, который патчит проект, относительно папки файла конфига. При
  нём `generate.out` — корень дерева патчей, тоже относительно папки файла конфига, а путь
  патча повторяет путь файла внутри upstream.

**Ключи не заданы.** Патч ложится рядом с файлом:

```
до                              после Generate Patch на src/a/b.cc
repo/                           repo/
└── src/a/                      └── src/a/
    └── b.cc                        ├── b.cc
                                    └── b.cc.sirp
```

**`"generate": { "out": "patches/" }`** — одна папка для всех патчей репозитория:

```
до                              после Generate Patch на src/a/b.cc
repo/                           repo/
├── sir.config.json           ├── sir.config.json
└── src/a/                      ├── patches/
    └── b.cc                    │   └── b.cc.sirp
                                └── src/a/
                                    └── b.cc
```

**`"upstream": "..", "generate": { "out": "patches" }`** в `src/brave/sir.config.json` —
проект внутри патчируемого кода хранит патчи деревом, которое повторяет этот код:

```
до                              после Generate Patch на src/chrome/browser/ui/browser.h
src/                            src/
├── brave/                      ├── brave/
│   └── sir.config.json       │   ├── sir.config.json
└── chrome/browser/ui/          │   └── patches/chrome/browser/ui/
    └── browser.h               │       └── browser.h.sirp
                                └── chrome/browser/ui/
                                    └── browser.h
```

`"upstream": "."` даёт такое же дерево внутри одного репозитория.

## Файл патча

Патч начинается шапкой — до первой пустой строки. Патч, порождённый ядром, которое
поставляется с расширением (sir 0.5.0):

```
Sir: 2
Target: src/a/b.cc
Base-Blob: 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
Sir-Version: 0.5.0
Grammar: tree-sitter-cpp@0.23.4
```

| Поле | Значение |
|---|---|
| `Sir` | номер формата патча; всегда первая строка |
| `Target` | файл, для которого патч, от корня репозитория. Ядро сопоставляет патч с файлом сначала по этому полю, затем по `generate.out` и `upstream` |
| `Base-Blob` | git-blob базы; только если база взята из git |
| `Sir-Version` | версия sir, записавшего патч |
| `Grammar` | грамматика tree-sitter и её версия |

В патче, написанном вручную, можно опустить все поля, кроме `Sir`. Без `Target` патч
сопоставляется по имени и месту; если и они не указывают на файл, об этом говорит первая
строка патча, и исправление — строка `Target:`.

Блок `# note` … `# end` непосредственно перед `# match` — комментарий к этому ханку:
незначащий текст с любого столбца, сопоставление его не читает.

```
# note
Повтор оставить: после рестарта сервер теряет первый запрос.
# end

# match cpp
    ...
```

- У ханка не больше одной заметки.
- Текст между ханками вне заметки — ошибка разбора.
- **Generate Patch** заметок не пишет: перегенерация патча удаляет его заметки и ханки,
  написанные вручную. Подтверждение перед перегенерацией называет ханки с заметками.

Редактирование `.sirp`:

- шапка, заголовки, операторы `...`, `>>>`, `<<<` внутри `# match` и заметки подсвечены;
  код ханка подсвечен как язык из его заголовка (Kotlin — только при расширении, которое
  даёт грамматику Kotlin);
- ханки и заметки сворачиваются; Outline и хлебные крошки перечисляют ханки с их
  состоянием;
- ввод `match` или `note` предлагает сниппет;
- хвостовые пробелы значимы: они видны и не обрезаются, перевод строки в конце файла не
  добавляется, форматирование при сохранении выключено, отступ — четыре пробела.

## Что показывает патч

Состояние открытого патча вычисляется без команды и пересчитывается при каждой правке
патча, кода, базы или конфига.

**Есть ли патч в коде** — одна метка после строки шапки и значок на имени патча в
Explorer и на его вкладке:

| Метка | Значок | Значение |
|---|---|---|
| `✓ applied` | `✓` зелёный | в коде есть всё, что пишет каждый ханк |
| `○ not applied — the code is its base` | `○` синий | код равен своей базе — как в свежем клоне upstream |
| `⚠ the code changed since the patch` | `≠` жёлтый | в коде уже нет того, что пишут некоторые ханки; перегенерация патча сохранит правки |
| `◌ nothing to check — the base is the saved file` | — | база — сохранённый файл, и код равен ему, поэтому определить наличие патча нельзя; с базой из git — можно |

У патча с проблемой значка нет: его имя уже красным отмечает Problems. Метка и значок
сохраняются после закрытия вкладки — до следующего открытия патча или запуска Check All.

**Ложится ли каждый ханк** — линза над каждым `# match`. Щелчок ведёт к месту, как Go to
the Other Side:

| Линза | Значение |
|---|---|
| `🟢 src/a.cc:413` | ханк ложится на эту строку: в коде, если патч применён, иначе в базе |
| `🟢 src/a.cc:413 · depends on an earlier hunk` | ханк ложится, а его цель появляется только после применения более раннего ханка |
| `🟡 differs from the code — regenerate?` | ханк ложится, но код в этом месте изменился |
| `🔴 anchor 3 of 5 not found` | шаблон останавливается на якоре, которого в базе нет |
| `🔴 fits 4 places` | шаблон неоднозначен, ему нужно больше контекста |

**Problems и подсветка:**

- Сломанный якорь подчёркнут на своей строке; причина — в Problems.
- Ханк, который никуда не ложится, выделен красным фоном, ханк, которого в коде больше нет, —
  жёлтым; оба отмечены на полосе прокрутки.
- Если не разрешается ничего (нет целевого файла, нет базы), одна строка вверху патча
  называет причину, и Problems показывает её на шапке.
- Патч, файла которого больше нет в upstream, — *осиротевший*; **Delete Patch…** после
  подтверждения перемещает его в корзину.
- Если ветки или коммита базы нет в репозитории, расширение предлагает сделать fetch.

**Лампочка** (Quick Fix, `Ctrl+.`, на macOS `⌘.`) на сломанном или съехавшем ханке
предлагает подходящие ему действия: **Show How Far It Got**, **Show the N Places It
Fits…**, **Go to Hunk N** (ханк прямо перед ним — у ханка, зависящего от более раннего),
**Regenerate Patch**. Действия, которые только показывают, идут первыми; переписывающее
действие никогда не выбрано по умолчанию.

**Строка состояния:**

| Активный файл | Строка состояния | Щелчок |
|---|---|---|
| патч | `S.I.R: 3/4 hunks` — сколько ханков разрешается против базы | журнал последнего разрешения |
| файл кода с патчем | сторож: `matches its patch`; `edits not in the patch` (сборка из патча их потеряет); `patch not applied` | Show Edits Not in Patch или Preview Patch |
| файл кода без патча | его база: `saved file`, `base HEAD:src/a.cc @ 4f1c2e2`, `new file`, `base unavailable` | Show Base |

**Generate Patch** доступна для файлов, для языка которых у ядра есть грамматика. На любом
другом файле команда отказывает, ничего не отправляя, если язык не задан в
`sir.language`.

## Когда синтез не может привязать правку

Если ядро не может построить шаблон для правки, ошибка предлагает **Write by Hand**:

1. Открывается несохранённый черновик: все ханки, которые легли, и один, который нужно
   написать для этой правки.
2. Ханк черновика, который не ложится, отмечен на своей строке.
3. Линза **▶ Continue Generate** над черновиком отправляет его в ядро, и синтез
   продолжается от написанных ханков.
4. Шаги повторяются, пока не привязана каждая правка; затем патч записывается.

## Применение патчей

Патч всегда накладывается на свою **чистую базу из git** — ревизию, которую называет
`generate.base`, — и никогда на сам код: на код, где патч уже есть, ядро записало бы
каждый ханк второй раз. Результат определяется состоянием кода:

| Код | Apply Patch |
|---|---|
| равен результату | сообщает об этом и ничего не пишет |
| равен своей базе | заменяется результатом в редакторе, без сохранения; одно Undo возвращает прежний текст |
| содержит правки, которых нет в патче | спрашивает: **Generate Patch** сохраняет правки в патче, **Overwrite** отбрасывает их, **Show Edits Not in Patch** показывает их |
| любой, и какой-то ханк не ложится на базу | отказ с предложением **Preview Patch**; частично ничего не применяется |
| любой, и база — сохранённый файл | отказ: Apply требует базы из git |

У патча, готового к применению (код равен базе из git, все ханки ложатся), над шапкой
стоит линза `▶ Apply to src/a.cc · 2 hunks | Preview`.

**Apply All Patches** решает судьбу каждого патча по той же таблице и пропускает каждый,
который потребовал бы вопроса.

- До 50 файлов: изменения проходят через Refactor Preview редактора, где любой файл можно
  исключить; одно Undo отменяет все изменения.
- Больше 50 файлов: сначала сводка и подтверждение, затем файлы записываются на диск;
  откат — через git.
- Файл записывается, только если его текст отличается от результата.

## Настройки

Генерацию настраивают два слоя:

- **`sir.config.json`** — политика проекта. Файл хранится в репозитории, поэтому одна и
  та же пара версий файла даёт один и тот же патч в терминале, в редакторе и в CI.
  Расширение ищет его так же, как CLI: от папки файла вверх до корня репозитория; конфиг
  выше корня репозитория не применяется никогда. Все ключи и их компромиссы описаны в
  [README sir](https://github.com/Danil-Varakin/S.I.R#configuration).
- **Настройки редактора `sir.*`** — личное переопределение одного разработчика. Каждая
  настройка соответствует ключу `generate.*` с тем же путём.

Приоритет — как у флага командной строки над файлом конфигурации:

```
встроенное значение  <  sir.config.json  <  настройка sir.*
```

| Настройка | Ключ конфига | Значения | По умолчанию (не задано ни настройкой, ни конфигом) | Что делает |
|---|---|---|---|---|
| `sir.out` | `generate.out` | путь | рядом с файлом | Куда пишутся патчи. Путь, оканчивающийся на `.sirp`, — файл патча; любой другой путь — папка, в которую ложится `<имя файла>.sirp`. При `upstream` в конфиге — корень дерева патчей |
| `sir.language` | `generate.language` | имя языка ядра | по расширению файла | Язык файла вместо определённого по расширению |
| `sir.exact` | `generate.exact` | `true`, `false` | `false` | `true`: результат должен воспроизводить новый файл байт в байт; `false`: строки сравниваются после нормализации |
| `sir.bridgeGap` | `generate.bridgeGap` | целое ≥ 0 | `0` | Правки, разделённые не более чем этим числом неизменённых непустых строк, объединяются в один ханк |
| `sir.parents.min` | `generate.parents.min` | целое ≥ 0 | `1` | Сколько объемлющих блоков несёт каждый шаблон. `0` допускает шаблон без родителя, который съехавшие соседи могут увести в другую функцию |
| `sir.parents.max` | `generate.parents.max` | целое ≥ 0, `"all"` | `"all"` | Наибольшее число объемлющих блоков в шаблоне; `"all"` — до самого внешнего |
| `sir.parents.detail.base` | `generate.parents.detail.base` | целое ≥ 0 | `0` | Сколько уровней скобок выписывается в заголовках родителей, начиная с внешнего: `0` даёт `foo( ... )`, `1` — `foo(bar( ... ))`. Влияет на читаемость и устойчивость к дрейфу, но не на корректность |
| `sir.parents.required` | `generate.parents.required` | `true`, `false` | `false` | `true`: генерация завершается ошибкой вместо отступления к шаблону без родителя |
| `sir.siblings.min` | `generate.siblings.min` | целое ≥ 0 | `0` | Сколько соседних значимых строк несёт каждый шаблон, с каждой стороны |
| `sir.siblings.max` | `generate.siblings.max` | целое ≥ 0 | `8` | Наибольшее число соседних значимых строк с каждой стороны; `0` запрещает соседей, и привязка остаётся чисто структурной |
| `sir.siblings.detail.base` | `generate.siblings.detail.base` | целое ≥ 0 | `0` | Сколько уровней скобок выписывается в якорях-соседях, начиная с внешнего |
| `sir.base.head` | `generate.base.head` | `true`, `false` | `false` | `true`: база — файл в последнем коммите текущей ветки. `false`: база — сохранённый файл, даже если конфиг называет базу из git. Подразумевается, если задана `sir.base.branch` или `sir.base.commit` |
| `sir.base.branch` | `generate.base.branch` | имя ветки, локальной или удалённой | текущая ветка | База — файл в последнем коммите этой ветки |
| `sir.base.commit` | `generate.base.commit` | ревизия: sha, тег, `HEAD~3` | последний коммит ветки | База — файл в этом коммите. Если задана `sir.base.branch`, коммит должен принадлежать этой ветке |
| `sir.base.eol` | `generate.base.eol` | `repository`, `worktree` | `worktree` (в CLI — `repository`) | Окончания строк базы, прочитанной из git: `repository` — как файл хранит git, `worktree` — как в файле на диске. Действует только для базы из git |

- **Незаданная настройка в ядро не отправляется** и потому не может перекрыть конфиг.
  Заданная действует для этого разработчика, даже если её значение совпадает со значением
  по умолчанию.
- **`sir.base.head`, `sir.base.branch`, `sir.base.commit`** задают базу целиком:
  любая из них, будучи заданной, заменяет весь `generate.base` конфига.
- **`sir.base.eol` по умолчанию `worktree`** в редакторе, тогда как ядро и CLI по
  умолчанию берут `repository`. Редактор сравнивает базу с буфером, а буфер содержит файл
  в том виде, в каком он лежит на диске; при `core.autocrlf` git хранит LF, а в файле CRLF,
  и база с окончаниями репозитория пометила бы изменённой каждую строку.
- **Журнал** при каждой генерации называет, какие значения взяты из конфига, а какие — из
  настроек:

  ```
  config: /repo/sir.config.json applied generate.parents.min; overridden by editor settings: generate.bridgeGap
  config: none, built-in defaults only
  ```

## Недоверенный workspace

В workspace, которому не выдано доверие:

- патчи порождаются, проверяются и навигация работает как обычно;
- собственная настройка workspace `sir.out` не действует;
- патч, который `sir.config.json` этого workspace отправляет за его пределы, пишется
  только после подтверждения;
- **Init Config** не создаёт файл.

## Журнал

Канал вывода *S.I.R* (**Sir: Show Log**) записывает каждый запрос и его длительность;
`resolve` дольше секунды записывается как предупреждение. Сообщения обмена с ядром
содержат фрагменты патчируемых файлов и пишутся только на уровне *Trace*
(**Developer: Set Log Level…**).

## Известные ограничения

- **Apply требует базы из git.** С сохранённым файлом в роли базы Apply отказывает;
  `sir apply` в терминале в этом случае работает.
- **Нельзя применить отдельный ханк.** Apply накладывает патч целиком.
- **Перегенерация удаляет заметки** и ханки, написанные вручную.
- **Один файл — один патч.** Второго `.sirp` у файла быть не может.
- **Большие файлы с множеством правок** могут генерироваться минутами; уведомление о
  прогрессе позволяет отменить генерацию в любой момент.
